## 1. Assumptions

The three problem invariants and four scope assumptions below are upstream of every decision in Section 2 and Section 3. If any of these change, the design that follows changes.

| # | Assumption | Source | Consequence |
|---|---|---|---|
| A1 | No ground truth — output is a synthesized report, not a labellable answer | problem framing | Quality is inferred from indirect signals (grounding, calibration, reproducibility, ablation deltas) — never from a single accuracy number |
| A2 | Context is finite — a 200K window cannot hold every relevant source | problem framing | Every box is implicitly a context-allocation choice |
| A3 | Hallucination is the default failure mode — plausible-but-wrong is the LLM's natural register | problem framing | A "no defense" pipeline fails silently; defenses must be active and post-hoc-checkable |
| A4 | No model training in scope | assignment Section 2.4 + earlier scope plan, "depth-vs-breadth" section | Depth must live at inference time |
| A5 | "Depth over breadth" — two contributions defended deeply, not six surveyed | assignment Section 1, Section 2.4; earlier scope plan, "calibration" section | v1 carries 2 contributions; everything else lands in v0.1 or is cut |
| A6 | Single run is the deliverable unit — no cross-run memory, no fine-tuning loop | scope choice | Reproducibility eval works run-vs-run, not session-vs-session |
| A7 | Cost matters but is not the optimization target — order-of-magnitude visibility is enough | earlier scope plan, "cost" section | Per-stage cost is observable (P8) but not optimized; price table is coarse |

## 1.5 v0 → v0.1 as the engineering-hardening pass

The v0 → v0.1 step is the **engineering-hardening pass** of this submission. v0 was the architecturally-complete baseline; v0.1 carries the same architecture but absorbs thirteen polish items that turn it from a runnable prototype into something inspectable, reproducible, and robust to real-world fetch surfaces. No new architectural contribution lands here — every distinctive idea (the re-fetch verifier, the shape-aware planner) is held for v1.

The thirteen polish items group cleanly under four E&I themes:

| Theme | Polish items |
|---|---|
| Observability and debugging surface for multi-agent workflows | P8 (per-stage cost), P9 (per-stage latency), P10 (`RunMetadata`), P11 (`ToolMix`) |
| Tool integration robustness and graceful degradation | P2 (typed `FetchResult`), P3 (paywall + bot heuristics), P4 (URL pre-check), P5 (three-strikes domain memory) |
| Reproducibility infrastructure | P12 (`subquestion_jaccard`), P13 (decomp-bounds sweep), P10 (commit-pinned run metadata) |
| Data hygiene at the source layer | P6 (source-quality lookup), P7 (per-finding provenance) |

Two non-polish patches sit alongside the P-list: BUG #1 (researcher SYSTEM prompt rewritten extract-as-you-go) and BUG #2 (`search_papers` retry + sticky back-off). These aren't classified as polish because they fix latent v0 defects that would have made the polish layer unmeasurable — without BUG #1, v0 returned zero findings on realistic prompts and the rest of the hardening had nothing to instrument.

One new pipeline stage — the final exporter (Component 7) — is structurally a presentation-layer addition rather than a research contribution. It's the only architectural change in v0 → v0.1, and it's E&I in motivation: the user asked for output-format flexibility; the writer's grounding contract shouldn't bear that load.

This framing affects what the doc treats as load-bearing: agent orchestration, observability, debugging, fault tolerance, latency / cost, deployment-grade infrastructure. The depth pitch for v0 → v0.1 is E&I throughout.

## 2. Architectural framing decisions

Four decisions sit *above* every per-component design in Section 3. They are stated here once and assumed by the rest of the doc. Each is a candidate the interviewer will probe.

---

### F1 — Multi-agent fan-out

**Decision**

- N async sub-agents under a semaphore
- One sub-agent per sub-question
- Each with an independent LLM context window
- Sub-agents communicate only via the structured findings store (F4); never via shared LLM context
- Granularity: per-sub-question — not per-source, not per-document

**Reasoning** *(two arguments, neither directly tested against a single-agent baseline in v0.1)*

- **(1) Context hygiene — primary**
    - A researcher reading 5–10 pages produces a 100K+ token trace
    - N such traces in one shared context would starve the writer by the time fan-out completes
    - Fresh contexts let each sub-question be pursued to its own depth, bounded by complexity rather than queue position
    - Combined with F4, isolation blocks framing leak between stages — researcher prose cannot reach the writer; only `Finding` records do
- **(2) Parallelism — secondary**
    - `asyncio.gather` reduces wall-clock from O(N) to O(1)
    - Real but secondary; if it were primary, single-agent with concurrent tool calls would suffice
- **Why per-sub-question is the right granularity**
    - Most sub-questions need 3–6 sources to triangulate → per-source spawns more agents than the work justifies
    - Reading thirty papers at once exhausts context → single-agent struggles on long-prompt research
- **Independent convergence on this pattern:** Anthropic's research system, STORM, WebGPT, GPT-Researcher

**Status of the claim**

- Design commitment grounded in Section 1 constraints and prior art — not an empirical result
- **v0.1 did not run a single-agent ablation on the same prompts**
- Statements about multi-agent's context advantage are predictions from the reasoning, not measurements
- Single-agent vs multi-agent comparison on the Section 6 test prompts is open work — would confirm or force revision

**Alternatives rejected**

- Single-agent serial loop — predicted to waste context, serialize I/O (addressed as the strongest counter below)
- Per-source sub-agents — coordination overhead expected to exceed context savings
- Shared-context researchers — defeats the hygiene argument; biases toward early discoveries
- Hierarchical multi-agent — premature at v0.1's scale (~5 researchers)

**Strongest counter**

- **arxiv 2604.02460** — *"Single-Agent LLMs Outperform Multi-Agent Systems on Multi-Hop Reasoning Under Equal Thinking Token Budgets"*
- Argues compute-controlled single-agent matches or beats multi-agent on reasoning tasks
- Without a v0.1 single-agent baseline to push back with, this paper is currently the closest empirical evidence on the question — and it cuts against multi-agent
- Defensible position:
    - Their setting: multi-hop reasoning over a fixed corpus
    - v0.1's setting: open-web research with unbounded source space and bounded context per source
    - Compute spent *reading* dominates compute spent *reasoning*
    - Their compute-parity result may not transfer
- But "may not transfer" is a hypothesis until measured

**Cost accepted**

- Multi-agent forces a reconciler, writer, and critic — single-agent could fold these into one loop
- Three extra LLM calls per run
- Traded for the context isolation the reasoning prefers

**Failure modes**

| Failure | Trigger | v0.1's response |
|---|---|---|
| Duplicate work | Overlapping sub-questions from a noisy decomposition | Decomposer "no summarize-X" rule (Component 1); not a guarantee |
| One slow researcher gates the gather | A single sub-question's fetch hangs | Per-fetch 15s timeout (Component 2); semaphore caps concurrency, not duration |
| Writer cannot synthesize across N narratives | Findings pool has no shared frame | Reconciler surfaces contradictions (Component 4); claim→finding-index forces grounding (Component 5) |
| No cross-researcher escalation | Researcher A finds X; Researcher B (who would benefit) is in a different context | **Unaddressed.** Cost of fresh contexts. Section 6: `note_uncertainty = 0` across 591 tool calls — researchers finish in isolation, never escalate |

**Open work**

- Single-agent vs multi-agent ablation on the Section 6 test prompts
- Until that runs, F1's claim is "this is the design and here is the reasoning," not "this is the better design empirically"

**v0.1 amendment**

- None at the architecture level
- P11 (`ToolMix`) and P9 (per-stage wall-clock) make the fan-out's tool-spend and gather-time observable for the first time

### F2 — Plain Python orchestration (no agent framework)

**Decision**

- `asyncio.gather` + semaphores + ordinary function calls
- No agent framework (LangGraph, CrewAI, AutoGen)
- Pydantic for schema validation; explicit per-call retry/backoff

**Reasoning**

- Pipeline is a chain (decompose → fan-out → reconcile → write → critique → revise-once → emit) with one conditional. A graph framework is a category mismatch for a chain.
- Retry semantics need to be call-specific:
    - Decomposer retries on schema fail only — not on transport errors
    - Reconciler doesn't retry on schema fail — zero contradictions is valid output
    - Generic `RunnableRetry` would over-retry (replay rate-limited calls) or under-retry (skip valid-output cases); ~30 LOC explicit covers the cases
- F4's structured-handoffs contract conflicts with frameworks shipping shared mutable state (CrewAI) — disabling the default is more code than typed function arguments
- At v0.1's scale (one process, 30–80 LLM calls/run), `track_stage` + per-call cost log (~50 LOC) is equivalent to LangSmith
- Right revisit point is v1's shape classifier — conditional branching across 4+ shapes makes LangGraph the right tool

**Status of the claim**

- v0.1 did not build a parallel LangGraph / CrewAI / AutoGen implementation
- LOC counts are from existing code; the claim that a framework would not save substantial design work is reasoning, not measurement

**Alternatives rejected**

- LangGraph — DAG / conditional edges; pipeline has neither
- CrewAI — shared memory; conflicts with F4
- AutoGen — conversation paradigm; wrong shape for a structured pipeline
- Plain Python without semaphores — risk of unbounded concurrency

**Cost accepted**

- ~30 LOC explicit retry/backoff (LangChain `RunnableRetry` would replace)
- ~50 LOC `track_stage` + cost aggregation (LangSmith would replace)
- No declarative pipeline view — readers trace control flow through `orchestrator.py`

**Failure modes**

- New LLM call site without explicit retry → easy to forget (mitigated: only ~5 LLM call sites in v0.1)
- No declarative pipeline visualization → readers trace through code
- `track_stage` decorator is human discipline, not framework guarantee

**When to revisit**

- v1 ships shape-aware branching → LangGraph becomes cheaper than `if/elif` dispatch
- Per-tool-call distributed tracing becomes a real need (multi-host or 1000+ calls/run) → LangSmith pays off
- Team grows past one author → framework conventions reduce onboarding cost

**v0.1 amendment**

- None — orchestration model unchanged
- P8 / P9 / P10 add the observability a framework would have given

### F3 — Single LLM family (Anthropic Claude) for every role

**Decision**

- Anthropic Claude family across all roles (decompose / research / reconcile / write / critique / judge)
- Within-family tiering by role:
    - researcher = `claude-haiku-4-5` — high tool-call volume, tier-1 TPM caps
    - writer / critic = `claude-sonnet-4-6` — synthesis quality
    - judge = `claude-opus-4-7` — eval rigour; intentionally **different from producer** to avoid same-model self-grading bias

**Reasoning**

- Surveyed deep-research-model leaderboards before committing — most usefully O-Researcher (OPPO, Jan 2026, arxiv 2601.03743) Figure 1
- **Honest reading of Figure 1(a):** Claude-3-7-Sonnet scored **40.67**, *below* OpenAI o3 (43.71) and GPT-5 (46.77). 13-point spread across the closed-source frontier (Gemini-2.5-Pro 35.12 → GPT-5 46.77). Claude was not at the top of the most recent published comparison.
- **The choice was constraint-driven, not quality-driven:**
    - Anthropic API access was the easiest path for the timeframe (one author, two days)
    - Cross-vendor wiring would burn build time without empirical evidence it would change v0.1's outcomes
- v0.1 uses Claude-4.x (haiku-4-5 / sonnet-4-6 / opus-4-7) which post-dates the survey snapshot — but the choice was made knowing Claude-3-7-Sonnet ranked third of four closed-source frontier on Figure 1, *not* on a claim that Claude-4.x has closed the gap (which is untested here)
- Within-family tiering does the cost / capability differentiation that mixed providers would otherwise provide
- Judge ≠ producer principle: same-model eval inflates scores via shared bias

**Status of the claim**

- v0.1 did not run the same pipeline against GPT / Gemini / open models per role
- Figure 1's data is January 2026 and tests Claude-3-7-Sonnet, not the Claude-4.x models v0.1 uses; the gap may have closed, may not have
- "Claude is good enough for this task" is on faith from practical experience, not measured against this batch

**Alternatives rejected**

- Mixed providers per role (e.g., GPT writer + Claude critic) — adds integration cost without measured benefit
- OpenAI-only (despite ranking higher in Figure 1) — would have required different API integration and rate-limit accounting; not chosen on practical access grounds
- Local models — capability gap on tool-use loops + structured output at v0.1's complexity

**Cost accepted**

- Vendor lock-in: Anthropic's pricing, rate limits, model availability, policy changes
- Single point of failure: Anthropic outage = full system down (no degraded-mode fallback)
- Made the choice knowing Claude-3-7-Sonnet was below frontier-leader on the most recent published comparison; no measurement of whether v0.1's Claude-4.x setup would beat / match / lose to GPT-5 or o3 on the Section 6 prompts

**Failure modes**

- Vendor outage → full system down
- Mid-deployment model deprecation → forced migration; P10 metadata helps reproduce old runs but doesn't undo it
- Per-role tier choices are intuition-driven, not measured — a role might be over- or under-provisioned

**When to revisit**

- Time available to run cross-vendor ablations on the Section 6 prompts (would confirm or force a switch)
- One role visibly underperforms its Claude tier and another vendor's tier looks better
- Production needs degraded-mode fallback during vendor outages
- Local-model capability closes the gap on tool-use loops + structured output

**v0.1 amendment**

- P10 (`RunMetadata`) records model id per role so a saved run is reproducible against the model snapshot
- See `v0.1_errors.md` E1 — there is a config drift between the dataclass default and `load()` fallback for `researcher_model`; the Section 6 batch ran with the documented haiku tier only because `RESEARCHER_MODEL` was set in `.env`. A fresh checkout without that env var would default to sonnet for the researcher.

### F4 — Memory & context allocation

**Decision**

- Per-stage context isolation — each researcher gets a fresh LLM context window
- Cross-stage data passes only via structured objects: `Decomposition`, `Finding[]`, `UncertaintyNote[]`, `Contradictions`, `Report`
- Writer never reads researcher reasoning; critic never reads writer reasoning
- Kept across stages: the five structured artifacts above
- Discarded after each stage: in-researcher tool traces, writer's intermediate prose, critic's intermediate critique

**Reasoning**

- F4 is the mechanism that makes F1 work — multi-agent fan-out is only worth the coordination cost if isolation pays off, and F4 is what enforces the isolation
- Structured handoffs are auditable: every `Finding` is a typed Pydantic object (`claim + evidence + source_url + confidence + ids`); the writer's input is fully inspectable
- Writer-blind-to-researcher and critic-blind-to-writer are structural, not policy — no code path passes the discarded data, so the constraint is impossible to violate by construction
- A2 (finite context) + A3 (hallucination-default): isolation prevents one researcher's tool trace from crowding another's room and limits framing leak between stages

**Status of the claim**

- v0.1 did not run a shared-context vs structured-handoffs ablation
- The framing-leak-prevention claim is structural reasoning, not measurement
- Section 6 batch shows no context overflow on any stage and stable cost shape — consistent with the design, not a direct test

**Alternatives rejected**

- Single shared context across stages — defeats A2 (context starves with N researchers' tool traces)
- Per-source sub-contexts inside a researcher — deeper hierarchy, marginal gain
- Explicit context summarization between stages — adds an LLM call per handoff for marginal benefit over typed artifacts

**Cost accepted**

- No cross-researcher escalation: researcher A cannot signal researcher B even if A's finding would unlock B's path
    - Section 6 evidence: `note_uncertainty = 0` across 591 tool calls — researchers finish in isolation
- Discarded data has audit value: when a run goes wrong, the researcher's tool trace is often where the issue lives. P11 records tool *counts* but not trace content; debugging requires a re-run with verbose logging
- Writer sees `Finding[]` count but not the *effort signal* (e.g., 25 tool calls for 1 finding vs 4 for 4) — P11 recovers this at run-metrics level, not at writer-prompt-input level

**Failure modes**

- Bad run is hard to debug from saved state alone — full trace lives only during runtime
- Cross-researcher overlap (A and B both researching the same thing) is invisible to either researcher
- Writer can't weight findings by source effort — a one-shot easy finding looks the same as a hard-won one

**When to revisit**

- v1 shape classifier ships with DISCOVERY shape, where cross-researcher fertilization could unlock dead-end paths
- Scale grows past ~5 researchers and isolation overhead becomes meaningful
- Debug-mode trace logging needed → polish item, not a structural change

**v0.1 amendment**

- None at the architecture level
- P11 (`ToolMix`) makes researcher-level tool spend observable
- P10 (`RunMetadata`) preserves model id and config snapshot per role
- P9 records the gather-duration of the fan-out (≈ max), making parallelism observable

### Component 1 — Decompose

**Purpose.** Turn an unstructured user prompt into 3–7 sub-questions with rationales, validated against a Pydantic schema.

**Decision (v0 baseline; carried unchanged into v0.1)**

| Aspect | Choice |
|---|---|
| Output | One LLM call producing structured `Decomposition` (sub-questions + rationale per sub-question) |
| Validation | JSON validated against Pydantic schema; up to 2 retries on schema-validation failure |
| Count bound | Clamped to `[3, 7]` after the planner returns |
| Prompt rule | "no summarize-X" — forbids degenerate sub-questions like "summarize the input" |
| Containment style | Structural enforcement, not policy (same pattern as F4) |

**Reasoning**

| Choice | Why |
|---|---|
| Decomposition is the first stage | Every downstream stage scopes against the plan; a bad plan poisons the whole run |
| Schema validation as containment | LLM is free to think; system enforces structure (count, rationale presence, no empty fields) |
| One LLM call (not multi-step) | At v0.1's scope, marginal value of plan-then-revise isn't worth the extra calls |
| Floor of 3 | Prevents under-scoping complex prompts (one sub-question = no decomposition) |
| Ceiling of 7 | Prevents over-scoping simple prompts (cost balloons with N researchers in fan-out) |
| "No summarize-X" rule | Prevents the most common LLM failure mode on this task |

**Alternatives rejected**

| Alternative | Why not |
|---|---|
| Fixed who/what/why/how template | Too rigid; real research questions don't always have all four |
| No decomposition (let one agent figure it out) | Burns context, no parallelism, no clean way to track coverage |
| Multi-step planner (plan then revise plan) | Overkill at v0.1's scope |
| Looser/tighter bounds (`[2, 5]` / `[4, 10]`) | Addressed by P13 below |

**v0.1 changes**

| # | Type | Change | What it closes | Exercised in Section 6? |
|---|---|---|---|---|
| (source) | No-op | Decomposer source code unchanged from v0 — schema, prompt, retry logic, clamping all identical between versions | — | — |
| P13 | Polish | Empirical decomposition-bounds eval (`eval/decomp_bounds.py`). Sweeps `(2,5)` / `(3,7)` / `(4,10)` on every benchmark prompt; reports mean count, % at floor / ceiling, intra-plan token-Jaccard. Decompose-only (no fan-out), cheap end-to-end. | Bound choice was intuition-supported only | Infrastructure built; **not yet run** on Section 6 prompts |
| P12 | Polish | Plan reproducibility metric `subquestion_jaccard` added to `eval/metrics/reproducibility.py`. Paired with `claim_jaccard` from one CLI invocation. | Distinguishes planner randomness from downstream noise | Not run for v0.1 in this batch |
| P8 / P9 | Polish | `track_stage("decompose")` wraps the decompose stage; per-stage cost / token / wall-clock surfaced on `RunMetrics.per_stage` | Decompose-stage attribution was invisible at v0 | ✓ — surfaced the "decompose cost is small" finding |

**Status of the claim**

| Claim | Status in v0.1 |
|---|---|
| `[3, 7]` bound is empirically defensible | Infrastructure (P13) exists; **no `decomp_bounds_*.json` artifact in the repo** — defense remains intuition-supported |
| Plan stability is reproducible across runs | P12 not run on v0.1's Section 6 prompts; later-version reproducibility numbers don't apply here |
| Decomposer is not a cost concern | ✓ supported — median 1.5% of run cost, < 4% in every run |

**Deferred**

| Item | Why held |
|---|---|
| Shape classifier (DISCOVERY / EVALUATE / SPARSE_EMERGING / …) + lead+parallel topology | v1's second contribution; current planner treats every prompt shape identically. Anchored in Snell 2024. |

**Failure modes**

| Failure | Detail |
|---|---|
| Bad decomposition early | N researchers each pursuing the wrong sub-questions; downstream cost is wasted |
| Plan is single-shot | No mid-run revision based on what researchers find |
| "No summarize-X" is a prompt rule, not structural enforcement | Can be violated if the LLM rephrases "summarize" creatively |
| All prompt shapes get the same decomposition strategy | Highest-cost failure mode in v0.1 (see *Observed*) |

**Observed (2026-05-05 batch — see Section 6)**

| Observation | Detail |
|---|---|
| Coverage variance tracks prompt shape, not run quality | Discovery / sparse prompts (Runs 3, 4): 43% / 71%. Structured comparative (Run 5): 86%. Judge `overall` follows the same axis (2.5 / 2.5 / 4.0 vs 3.5+). |
| Decompose stage cost is consistently small | Median 1.5% of run cost, < 4% in every run. The failure surface is in *what gets decomposed*, not *how expensive*. |
| No P13 or P12 results for v0.1 to cross-reference | — |

**When to revisit / open work**

| Trigger | Action |
|---|---|
| Want to defend `[3, 7]` on data | Run P13 on the Section 6 prompts; either confirms `[3, 7]` empirically or forces revision (cheap; can be added later) |
| Want to separate planner randomness from downstream noise | Run P12 on v0.1's Section 6 prompts (later-version reproducibility numbers aren't v0.1's) |
| Prompt-shape failure mode | v1 shape classifier addresses it |

### Component 2 — Researchers

**Purpose.** One sub-agent per sub-question, run with `asyncio.gather` under a semaphore. Five tools, fresh context, explicit budgets.

**Decision (v0 baseline)**

| Aspect | Choice |
|---|---|
| Granularity | One researcher per sub-question (per F1 + F4) |
| Tools | `web_search`, `search_papers`, `fetch_url`, `save_finding`, `note_uncertainty` |
| Stop conditions | `min_findings_to_stop=3` OR `max_tool_calls=30` OR `unproductive_call_limit=10` |
| Per-fetch timeout | 15s |

**Reasoning**

| Choice | Why |
|---|---|
| One researcher per sub-question | F1 + F4: independent contexts let each sub-question be pursued to its own depth, not bounded by where it falls in a queue |
| Five-tool kit | Minimum to ground a claim end-to-end: search (web + papers) → fetch → save_finding / note_uncertainty. No tool is redundant; removing one breaks the loop. |
| OR'd disjunctive stop conditions | Multi-signal stop adds a per-researcher LLM call (A4: depth at inference time, not extra calls); marginal benefit; cut from v1 |
| 15-second per-fetch timeout | Bounds the gather's tail latency; the semaphore caps concurrency, not duration |

**Alternatives rejected**

| Alternative | Why not |
|---|---|
| Larger toolkit (browser, calculator, code-exec) | Surface area exceeds v0.1's evaluation depth |
| Single search tool | `search_papers` + `web_search` is the minimum to cover peer-reviewed and open web |
| Tool-free in-context retrieval | Defeats grounding — can't cite verbatim evidence to a URL |

### Component 3 — Findings store (the blackboard)

**Purpose.** Flat in-memory pool of structured `Finding` objects produced by all researchers, plus separate `UncertaintyNote` records. Serialized to JSON on output. Read by the reconciler, the writer, and the critic.

**Decision (v0 baseline)**

| Aspect | Choice |
|---|---|
| Data structure | Flat list — not hierarchical, not indexed |
| Storage | In-memory only; serialized to JSON on output |
| Mutation policy | Append-only during research |
| `Finding` shape | claim + verbatim evidence + source_url + self-reported confidence + researcher_id + sub_question_id |
| Uncertainty record | Separate `UncertaintyNote` schema (not collapsed into `Finding`) |

**Reasoning**

| Choice | Why |
|---|---|
| Flat list | The critic operates over the whole pool; hierarchy would require traversal and add complexity without information gain |
| In-memory only | Per-run lifecycle (A6: single run is the deliverable unit, no cross-run memory); persistent storage would be premature |
| Append-only | Audit trail — the critic and any post-hoc reviewer can see every finding produced, including ones that didn't survive into the report |
| Verbatim evidence required | The *contract* between research and verification. The critic's grounding check needs verbatim text to compare against retrieved page text. v1's re-fetch verifier will seek the exact same string on the live page. |
| Separate `UncertaintyNote` | Conflating with `Finding` (via an `is_uncertain` flag) would dilute every downstream consumer — the writer treats them differently; the critic ignores notes; the metrics differentiate "no answer" from "answer is poorly grounded" |

**Alternatives rejected**

| Alternative | Why not |
|---|---|
| Free-form research summaries | A1 — ungroundable; nothing for the critic to check against |
| Vector DB for findings | Corpus is small per run (≤30 sources); cosine search adds latency without benefit at this scale |
| Per-researcher private store + merge | Same effect as the shared blackboard with extra plumbing |
| Evidence-as-summary (paraphrase rather than verbatim quote) | Loses the critic's textual check; no live-page string to verify against |
| Multi-axis confidence at v0 | Premature. v0.1 introduces source-quality as a second axis (P6) — a deliberate single addition, not a wholesale move |
| URL-less claims | Defeats grounding; every finding must be traceable to a fetched page |

### Component 4 — Reconciler

**Purpose.** Detect contradictions across the findings pool. Surface them; do not resolve them.

**Decision (v0 baseline; carried unchanged into v0.1)**

| Aspect | Choice |
|---|---|
| Mechanism | Single LLM call scans the findings pool, emits contradiction descriptions |
| Output shape | `list[str]` — prose contradiction descriptions |
| Resolution policy | Surface conflicts; do NOT pick a winner |
| Validation | Schema-validated structured output |
| Prompt | Includes positive and negative examples to constrain interpretation of "conflict" |

**Reasoning**

| Choice | Why |
|---|---|
| Surface, don't resolve | A1 — honest disagreement is the deliverable, not noise. If two papers disagree, the report should say "they disagree, here is why" rather than "the truth is X." |
| Picking a winner is inappropriate | Vote / weight / recency all encode whichever bias the scheme carries; for an agent without ground truth, there's no defensible adjudication procedure |
| Single LLM call (not per-pair) | Per-pair LLM judgments are O(n²); one-pass scan over the pool catches headline disagreements at constant cost |
| Prose output, not typed | (v0 borderline call) Typed `Contradiction(description, finding_ids, severity, type)` would let the writer link contradictions to specific claim indices, but the writer doesn't currently link them even with prose, so the upgrade has no consumer yet |
| Examples in the prompt | The conflict-detection task is sensitive to how "conflict" is interpreted; positive/negative examples narrow the surface |

**Alternatives rejected**

| Alternative | Why not |
|---|---|
| Pick a winner (vote, weight, recency) | Encodes whichever bias the scheme carries; inappropriate for a research agent without ground truth |
| Skip contradictions entirely | Loses the most valuable signal in any contested topic |
| Per-pair LLM judgments over all findings | O(n²) calls; the single-pass scan catches the headline disagreements at much lower cost |
| Typed `Contradiction(description, finding_ids, severity, type)` at v0 | Borderline call held for v1 — without a writer that consumes the typing, the upgrade has no downstream effect |

### Component 5 — Writer

**Purpose.** Synthesize a structured `Report` from the findings pool. Every claim cites a list of supporting `finding_indices`.

**Decision (v0 baseline; carried unchanged into v0.1)**

| Aspect | Choice |
|---|---|
| Output | Structured `Report` — every claim cites `finding_indices` into the findings pool |
| Mechanism | Separate LLM call from the orchestrator |
| Prompt rules | No invention; no external knowledge; never paraphrase a claim past what its evidence supports; surface contradictions explicitly |
| Revision | Single-pass (the critic + revision loop is Component 6) |

**Reasoning**

| Choice | Why |
|---|---|
| Structured `Report` with finding indices | Linked claims-to-findings is what makes citation grounding *automatically checkable*. A free-form report would put the critic on text-vs-text — a much weaker signal. |
| Writer is a separate LLM call | Mixing control flow with synthesis would make the system harder to revise. Auditability — the writer's input (findings, contradictions, prompt) and output (`Report`) are both inspectable artifacts. |
| "No external knowledge" hard rule | A3 — the writer's natural register is plausible synthesis. Any claim added from training memory is unverifiable in the same loop, and unverifiable claims are exactly the failure mode the architecture is designed to catch. |
| "No invention; never paraphrase past evidence" | Constrains the writer to what the researchers retrieved; the critic's signal stays meaningful only under this constraint |
| Single-paragraph claims, not multi-paragraph | Multi-paragraph claims are harder to attribute to specific evidence indices; the citation surface gets diluted |

**Alternatives rejected**

| Alternative | Why not |
|---|---|
| Orchestrator writes the report | Mixes control flow and synthesis; harder to revise |
| Free-form report (no structured schema) | A1 — ungroundable; defeats automated grounding eval |
| Multi-paragraph claims | Harder to attribute to specific evidence; citation surface gets diluted |
| Soft style guide instead of hard rules | Lets the writer's "plausible synthesis" register through; the critic's signal degrades |
| Allow external knowledge as "common-sense" backfill | Once the writer can draw on memory, the critic can't tell whether a claim is grounded in retrieved evidence or in writer-internal knowledge |

### Component 6 — Critic + revision

**Purpose.** Independent verification of writer claims against cited evidence. If issues are found, trigger one writer revision; ship the result.

**Decision (v0 baseline; carried unchanged into v0.1)**

| Aspect | Choice |
|---|---|
| Critic mechanism | Independent LLM call; blind to writer reasoning |
| Critic input | Claims + cited findings + source URLs only |
| Critic output | Typed issues: `ungrounded` / `overstated` / `missing_citation` / `source_mismatch` |
| Critic scope | Text-vs-text only — no reach back to the live URL |
| Revision policy | Single-pass — if the critic flags, the writer revises once. The next critic check is final. Ship even if still flagged. |

**Reasoning**

| Choice | Why |
|---|---|
| Independent LLM call | Independence is the structural property. If the critic sees the writer's prose, it absorbs the writer's framing — a known failure mode in self-critique pipelines. |
| Blind to writer reasoning | The writer is the worst judge of whether its own claim is supported (committed to a justification); a fresh critic with claims + evidence only gets cleaner signal |
| Typed issues, not free-form | Free-form quality critique surfaces vibes, not failures. Typed issues are actionable — the writer's revision prompt addresses each issue type with a specific instruction; the eval suite computes per-category rates over time. |
| Text-vs-text scope (no re-fetch) | Re-fetch is held for v1 specifically so the v0.1-vs-v1 attribution stays clean. The fabrication-rate ablation is v1's headline experiment; v0.1 carrying the verifier would muddy the comparison. |
| Single-pass revision | A4 (cost discipline) — quality plateaus fast under iterative refinement; most issues fixable in one revision are fixed in one. Beyond one round, marginal recall is small relative to cost. |
| Ship even if still flagged (no caveats fallback) | Bounded revision with caveats fallback is held for v1 — same attribution-cleanliness reason as the verifier |

**Alternatives rejected**

| Alternative | Why not |
|---|---|
| Free-form quality critique | Vibes, not failures — produces opinions instead of typed issues that the revision prompt or eval suite can act on |
| Critic sees writer reasoning | Loses independence; would absorb writer framing |
| Pre-publication editorial pass instead of a critic | Mixes synthesis and verification; weaker fact-check signal |
| Fully programmatic (no LLM) critic | Token-overlap heuristics have high false-positive rates on legitimate paraphrases and high false-negative rates on subtle drift; LLM-as-judge handles semantic comparison reliably |
| Re-fetch verifier at v0.1 | Held for v1's first headline contribution; running it at v0.1 muddies the v0.1-vs-v1 attribution |
| Infinite revision loop | Cost grows linearly; quality plateau makes the marginal rounds wasteful |
| Bounded revision + caveats fallback at v0.1 | Held for v1 — same attribution-cleanliness reason |

### Component 7 — Final exporter

**Purpose.** Render the post-critic structured `Report` to the format the user actually asked for, and audit the rendered output against conditions extracted from the original prompt. New pipeline stage in v0.1; not on the P-list.

**Decision (new in v0.1)**

| Aspect | Choice |
|---|---|
| When in pipeline | After the critic + revision loop completes (post-critic, pre-emit) |
| Mechanism | Single LLM call on `cfg.writer_model` |
| Input | Original user prompt + `Decomposition` + `FindingsStore` + post-critic `Report` |
| Output | `FinalOutput` with rendered `content` (markdown) + per-condition `ConditionCheck[]` + flat `unmet_conditions` list |
| On-disk shape | Single `.md` file under `cfg.exporter_md_dir`; `content` written verbatim with a small prompt/format preamble |
| Diagrams | Fenced ```mermaid``` blocks only — no external images, no PDF toolchain |
| Default format | Narrative summary in markdown if the prompt doesn't specify |

**Reasoning**

| Choice | Why |
|---|---|
| Separate phase, not the writer's job | Writer's contract is grounding fidelity — every claim cites a finding, every finding's evidence verbatim. Asking the writer to ALSO satisfy presentation requirements muddies that contract; revisions for "use a table" can drag claims off their evidence. |
| Exporter is free to rewrite | Not bound by `supporting_finding_indices` semantics — it just RENDERS already-grounded content. Frees the writer to stay disciplined; frees the exporter to satisfy format requirements. |
| One LLM call (not multi-step) | Same cost-discipline pattern as the writer; quality plateaus fast on presentation tasks |
| Conditions audited explicitly | Surfacing prompt-derived conditions as a typed `ConditionCheck` list lets the user see what's missing without reading the full content. The `unmet_conditions` flat list is the at-a-glance signal. |
| Mermaid for diagrams | Self-contained markdown — single `.md` file works without external image or PDF toolchain |
| Exporter has no internal `track_stage` wrapper | Orchestrator owns stage timing and call-log tagging at the call site; the exporter itself is pure presentation logic |

**Alternatives rejected**

| Alternative | Why not |
|---|---|
| Writer renders to user format directly | Muddies the writer's grounding contract; revisions for "use a table" can pull claims off their evidence |
| No exporter (orchestrator emits raw `Report` JSON) | Misses the presentation layer; user with a "300-word memo" ask gets a structured object, not the memo |
| Multi-step exporter (plan → render → audit) | Quality plateaus fast on presentation tasks; one LLM call is sufficient |
| External image / PDF toolchain | Adds dependencies; mermaid embedded in markdown stays self-contained |
| Audit conditions in a separate later pass | One LLM call has the prompt + the rendered content available together; splitting loses the joint check |
| Programmatic condition extraction (regex / NER) | Misses implicit-but-load-bearing conditions; the LLM's read of the prompt is more flexible |

**v0.1 changes**

| # | Type | Change | What it closes | Exercised in Section 6? |
|---|---|---|---|---|
| (new) | New stage | Final exporter added in v0.1. Reads user prompt + post-critic `Report` → emits `FinalOutput` with rendered markdown + `ConditionCheck[]` + `unmet_conditions`. *Files:* `src/agent/exporter.py`, `src/state.py:FinalOutput`, `src/config.py:exporter_md_dir`. | v0 emitted only the structured `Report`; users with format-specific asks ("memo", "table", "300 words") got a structured object, not the rendered output | ✓ — exporter ran on every Section 6 run, produced a `.md` file per run |

**Status of the claim**

| Claim | Status in v0.1 |
|---|---|
| Splitting presentation from grounding preserves the writer's contract | ✓ supported by design — the writer's `supporting_finding_indices` semantics are unchanged from v0; the exporter rewrites freely without affecting them |
| Mermaid is sufficient for the diagram surface this batch needed | ✓ supported empirically — every run rendered cleanly to a single `.md` file; no run hit a diagram requirement that mermaid couldn't satisfy |
| `unmet_conditions` correctly surfaces what's missing | **Not directly audited in Section 6** — the list is in each run's `FinalOutput`, but no per-run review of "did the audit catch what was actually missing?" was done |
| Exporter cost is acceptable | ✓ supported — median 12% of run cost; range 7.7–20.9% |

**Deferred**

| Item | Why held |
|---|---|
| Per-stage `track_stage` wrapper inside the exporter | Orchestrator owns stage timing at the call site; the exporter itself stays pure presentation logic |
| Format negotiation with the user (clarification round) | Single-shot at v0.1 — exporter infers the format from the prompt or defaults to narrative-markdown; clarification would add latency without improving the common case |
| Programmatic condition extraction (regex / NER) | The exporter's LLM call extracts conditions by reading the prompt; programmatic extraction would miss implicit-but-load-bearing conditions |
| Non-mermaid diagram surfaces (Graphviz, PlantUML) | Single-file markdown stays self-contained; mermaid covers the common diagram classes the batch needed |

**Failure modes**

| Failure | Detail |
|---|---|
| Exporter could drop a claim needed to satisfy a condition | Hard prompt rule prohibits it ("Do NOT drop claims that are needed to satisfy a condition"), but enforcement is the LLM's interpretation, not a structural check |
| `unmet_conditions` list is the LLM's self-report | The exporter audits its own output; if too lenient, an unmet condition could be marked satisfied. The judge in Section 6's eval surface is the cross-check, but it's post-hoc, not in-line. |
| Format inference can be wrong on ambiguous prompts | If the prompt doesn't specify a format and the inferred default doesn't match user expectation, the user has to re-run; no clarification round at v0.1 |
| Mermaid doesn't cover every diagram class the user might want | Acceptable at v0.1's scope — flowcharts, sequence diagrams, class diagrams cover the common cases |

**Observed (2026-05-05 batch — see Section 6)**

| Observation | Detail |
|---|---|
| Exporter cost share | Median 12% of run cost; range 7.7–20.9% across the 6 runs |
| Exporter ran on every run | All 6 runs produced a `FinalOutput` and a `.md` file under `cfg.exporter_md_dir` |

| `unmet_conditions` populated, not audited | Each run's `FinalOutput` includes the list, but no per-run check was done to verify the LLM's audit matched reality |

**When to revisit / open work**

| Trigger | Action |
|---|---|
| `unmet_conditions` audit needs verification | Add a per-run sanity-check: pick 1–2 runs, manually verify the audit list matches what's actually missing |
| Run 5's 2-call exporter pattern recurs | Investigate the retry path in `exporter.py` — is it firing on schema fail, or another error? Track the trigger so the cost spike can be attributed. |
| Mermaid hits a coverage gap | Add a fallback path or a different diagram language; current scope is sufficient until evidence shows otherwise |
| User asks for a format the LLM can't infer | Add a clarification round before the exporter; today the user has to re-run with a clearer format spec |

### Component 8 — Metrics & observability

**Purpose.** Make a run inspectable end-to-end. Per-run `RunMetrics` answers "how did this run do?"; per-stage breakdowns answer "where did the cost / time / call go?"; metadata answers "against what algorithm version?"

**Decision (v0 baseline)**

| Aspect | Choice |
|---|---|
| `RunMetrics` per run | sub-questions covered, total findings, unique sources, revision rounds, coverage rate, grounding rate, elapsed seconds |
| Granularity at v0 | Per-run only — no per-stage breakdowns |
| Reproducibility envelope at v0 | None — no commit hash, no model ids, no config snapshot |
| Tool-selection telemetry at v0 | None |
| `final_grounding_rate` formula at v0 | `1 - n/(n+1)` for n outstanding critic issues — bounded but bug-laden (returns 0.5 for one issue regardless of total claim count) |

**Reasoning**

| Choice | Why |
|---|---|
| Handful of robust metrics, not a wall of decoration | A1 — quality signals are indirect; few well-chosen metrics > many noisy ones. Each metric answers a specific failure mode. |
| Per-run aggregation at v0 | Adequate for "did this run succeed?"; per-stage breakdowns deferred to v0.1 polish |
| Bounded grounding-rate formula | Designed to give a single number in [0, 1]; the v0 implementation got the shape right but the formula wrong (P1 fixes) |

**Alternatives rejected**

| Alternative | Why not |
|---|---|
| Wall of decoration metrics | Hides what's actually changing run-to-run; signal-to-noise drops |
| No metrics | Leaves "how did this run do?" unanswerable; runs become opaque |
| Per-run metrics only with no per-stage breakdown forever | Would leave "which stage just got expensive?" unanswerable; v0.1's P8/P9 close this |

### 6.5 Caveat — judge knowledge-cutoff false positives
